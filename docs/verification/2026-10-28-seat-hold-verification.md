## 테스트가 실제로 결함을 잡는지 확인

동시성 테스트는 구현 후에 작성해 처음부터 통과했으므로, 코드를 일부러 망가뜨려 실패하는지 확인한 뒤 되돌렸다.

- 선점의 `NX` 옵션을 제거 → "20명 동시 선점" 테스트가 실패했다.
- 결제의 중복 키 오류(`P2002`) 처리 제거 → "동시 결제" 테스트가 실패했다.

## 외부 검토(Codex)와 후속 수정

`codex review`로 브랜치 전체를 검토시켜 동시성 허점 2건을 받았다. 각각 재현 테스트를 먼저 작성해 실패(예약 10행 생성, 확정 1건 409)를 확인한 뒤 고쳤다.

- 동시 예약 생성 시 중복 행: 좌석 행을 `SELECT ... FOR UPDATE`로 잠그는 트랜잭션 안에서 조회와 생성을 처리하도록 변경.
- 동시 확정에서 늦은 요청이 선점 만료로 오판: 선점자가 없을 때 예약 상태를 다시 읽어 이미 `CONFIRMED`면 그대로 반환.

## 고친 문제

| 문제 | 수정 후 확인 |
|---|---|
| TTL 만료 후 DB 좌석이 `HOLDING`으로 남음 | 만료 후 목록이 `AVAILABLE`, 다른 사용자가 선점 가능 |
| 확정 후 선점 키가 남아 TTL 뒤 `SOLD` 좌석이 다시 선점됨 | 확정 시 키 삭제, `SOLD` 좌석 선점은 409 (TTL 경과 후에도) |
| 예약·결제에 선점자·소유자·금액 검사가 없음 | 403·400 확인 |
| 확정·취소가 예약과 좌석을 따로 갱신 | 트랜잭션으로 묶음. 좌석 갱신 실패를 주입해 예약이 `PENDING`으로 유지됨을 확인 |
| 같은 요청이 반복되면 오류 또는 중복 생성 | 선점·예약 생성·확정·취소·결제가 같은 결과를 반환 |

## 검증하지 않은 범위

- HTTP 부하·응답 시간 측정, 서버 여러 대 구성, 실제 결제 연동은 포함하지 않았다.
- 선점 요청과 확정이 정확히 겹치는 구간(선점이 DB의 `AVAILABLE`을 읽은 직후 확정이 커밋되는 경우)은 테스트하지 않았다. 이때 좌석은 `SOLD`로 유지되지만 선점 응답이 `HOLDING`으로 나가고 키가 TTL까지 남을 수 있다.
- 프런트엔드는 검증 대상이 아니다.
- 기존 `backend/test-concurrent-hold.sh`는 위 자동 테스트로 대체되며 삭제하지 않았다.
