# 좌석 선점 정합성 개선 설계

## 의도
Redis TTL 선점은 동작하지만, 선점 만료·결제 확정·예약 흐름에서 Redis와 DB 상태가 어긋나는 허점이 있다. 이를 고치고 동시성 시나리오를 자동 테스트로 검증해, 포트폴리오에 "문제 → 수정 → 검증"으로 쓸 수 있게 한다.

## 목표
- TTL 만료 후에도 좌석 상태가 어긋나지 않는다.
- 결제 확정된 `SOLD` 좌석은 다시 선점되지 않는다.
- 예약·결제는 선점한 본인만, 올바른 금액으로 진행한다.
- 확정/취소에서 예약·좌석 상태가 함께 바뀌거나 함께 실패한다.
- 위 항목을 실제 MySQL·Redis 대상 테스트로 검증하고 결과를 기록한다.

## 비목표
- 대기열, 정산 배치, 실제 PG 연동, 부하·성능 측정, 프런트엔드 변경.

## 제약
- 개발용 DB/Redis 데이터를 건드리지 않는다. 같은 서버의 `ticketing_test` DB와 Redis 별도 DB 번호를 사용한다.
- 기존 API 경로와 응답 형태는 유지한다.

## 접근 방식 (사용자 선택: A)
- A. 좌석 조회 시 Redis를 함께 읽는다 (선택). 선점 여부의 기준은 Redis. DB는 `AVAILABLE`/`SOLD`만 확정 상태로 보고, 조회 시 Redis 키가 살아 있는 좌석만 `HOLDING`으로 응답한다. 상태가 어긋날 여지가 없다.
- B. 요청 시 `heldAt` 기준으로 DB 정리: 기준이 두 곳이라 동기화 시점이 어긋남.
- C. 만료 이벤트/스케줄러: 인프라 증가, 지연. 설계문서가 이미 기각.

## 수정 사항
1. `hold`: DB가 `SOLD`인 좌석은 거부. Redis만 기록하고 DB에 `HOLDING`을 쓰지 않는다(그래서 DB 갱신 실패 시 키 정리가 필요 없다).
2. 좌석 조회: `MGET`으로 선점 키 확인, 키가 있는 `AVAILABLE` 좌석만 `HOLDING`으로 표시.
3. `confirm`: 선점 키 삭제, 예약·좌석 갱신을 `$transaction`으로 묶음.
4. `cancel`: 좌석 `AVAILABLE` 복귀와 키 삭제, `$transaction`.
5. 예약 생성: Redis 선점자가 요청 사용자인지 검사.
6. 결제: 예약 소유자 검사, 금액이 0 이하이면 거부.
7. `cancelHold`: 확인+삭제를 원자적으로 처리(Lua 또는 비교 후 삭제).

8. 멱등성(경량): 같은 사용자의 재선점은 성공으로 응답(TTL 유지), 이미 성공한 예약의 결제 재요청은 기존 결제 반환, 확정·취소 재호출은 같은 결과. `Idempotency-Key` 헤더 방식은 제외(후속 과제).

## 검증
- 동시 선점 10~20건 → 정확히 1건 성공, 나머지 409.
- 확정 후 키 만료 시점 이후에도 `SOLD` 좌석 선점 거부.
- TTL 만료 후 조회 시 `AVAILABLE`로 표시.
- 타인 선점 좌석 예약·결제 거부.
- 트랜잭션 실패 시 예약·좌석 상태 유지.

## 빌더에게 맡기는 것
테스트 러너 선택(Jest 권장), 테스트 DB 초기화 방식, Lua 스크립트 사용 여부.
